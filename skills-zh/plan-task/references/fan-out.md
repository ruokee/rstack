# 标注可并行单元

计划里已有两个或更多单元，且有人可能分别接手时，判断哪些单元可以标为 `fan-out`。标注表示：前提满足后，执行者可以同时开始，各自完成约定的结果。用户也可以选择逐个完成。两种做法使用相同的交付物、依赖和验收条件。

## 判断独立性

把每个单元分别交给一个接手者。假设其他人直到交付才回消息，问：**他能凭已有输入做完并检查自己的结果吗？调换完成顺序，会改变谁的结果吗？** 用以下事实回答：

- **输入和决定。** 每人开工所需的版本、接口含义和验收口径已经确定。多个单元可以读取同一份固定资料。如果 B 必须等 A 定字段含义或交出样本，就在 B 上写出这个前置结果；从该结果就绪的位置再看剩余工作。
- **写入和资源。** 找出每个单元会修改的文件、生成物、数据和环境，包括检查时的写入。不同目录的任务也可能重写同一份索引，或把对方正在用的测试库清空。把共享改动交给一个明确的单元；独占设备需要轮用时，分别写清哪些工作能并行、哪个检查要串行。
- **交付和汇合。** 每人知道自己交什么、怎样单独检查；接手结果的人知道在哪里对照、集成或验收整体。将汇合放在真正消费这些结果的步骤。只需要 A 的后续工作照常按 A 的依赖推进。

共同前提尚未满足时，可以写明将来何时可并行。若仍需各方边做边决定同一件事，就保留依赖或合回一个单元。不为凑出并行组而多拆任务。

## 在计划中标注

沿用计划原有的单元名或编号。在相关单元旁写一行 `fan-out（可选）`，点名可并行的成员、何时可以开始、由谁消费结果。单元正文已经说明的输入、写入范围和验收方式直接引用。没有合适的一组就省略标注。

例如，两种订单格式已有公开约定，各有自己的样例：

> **fan-out（可选）：CSV 和 JSON 解析器都可以现在开始，同时做或逐项做均可。导入命令接收两份结果。**
>
> 各解析器有自己的模块和测试数据，按本格式的样例核对订单和错误。由一人注册两种格式，通过命令导入两份等价样例，再读回预期订单。

若 CSV 的一个字段含义待定，指出哪些 CSV 工作依赖这个答案。JSON 可以按已有约定开工并完成。若两个解析器必须改写同一个生成文件才能核对结果，让一个单元负责写入，或只将冲突的检查改为逐项执行。其余工作照常推进。

## 执行时使用

执行者按当前前提、可用资源和用户选择安排工作。采用并行时，各自取得单元所需的上下文，按计划把结果交给接收方；选择串行时，保留原有依赖和汇合检查。发现共享约定改变时，撤销或收窄受影响的标注，保留其余仍适用的结果。写入标注本身不派工。
