# 映射上下文关系

上下文图，也称 Context Map，解释现有模型怎样接触、互相影响，并通过真实协作演进。提出变化前先识别各模型及适用范围。分别标明现有安排和提议安排。

## 描述关系

对每个接触点记录双方模型、交换信息、身份关联、语义转换、影响方向、变更协商及集成负责者。使用图时，解释箭头方向或标签的含义。

上游影响表示一方的模型或开发决定约束另一方的成功。数据可以同时双向流动。HTTP 调用方向、事件发布和业务影响回答不同问题。交付相互依赖时，即使技术数据只向一方流动，也可能需要合作。

## 判断集成价值

比较集成带来的实际收益与所需的转换和协调成本，计入重复工作及人工衔接。成本收益支持分离时，各行其道，也称 Separate Ways，让模型保持独立。将剩余业务义务交给能够履行的负责者。

既有混合区域可能缺少一致的内部模型边界。用大泥球，也称 Big Ball of Mud，标明它，并描述实际已经理解的接触点。按需要隔离其影响。整体重写作为另一项决定，需要对应理由及授权。

## 分配含义责任

在集成点决定消费者使用哪一方的模型。采用适用的上游模型属于遵奉，也称 Conformist。这节省转换工作，并让上游决定影响消费者的语言及演进。采用前检查消费者的规则；独立模型的收益需要值得其维护成本。

消费者需要自己的含义时，用防腐层，也称 Anticorruption Layer，承担语义转换。除字段名外，还需映射身份、单位、状态、失败及信息缺失。双方模型变化时维护映射。连接及表示细节由传输适配承担。一个实现可以承担这两项责任。与上游协商计划可以和语义转换并存。

交换信息时，约定字段含义，将其记录为发布语言，也称 Published Language，可以采用行业标准或项目契约。参与者按需在发布语言及内部模型之间转换。计入 schema 维护及语义演进成本。共享 schema 仍需要含义上的共识。

服务多个消费者的提供方可以通过开放主机服务，也称 Open-host Service，维护共同协议。明确预期消费者范围及演进契约。专用转换能够保持共同契约时，用它处理个别消费者的特殊需要。发布 API 本身仍留下这些选择待定。

共享内部领域概念需要更紧密的承诺。共享内核，也称 Shared Kernel，让双方共同控制一小部分约定模型及关联代码或 schema 的变化。保持范围可理解，共同整合变化，并接受由此产生的协调及耦合演进。共享日志和 HTTP 工具属于普通技术复用。

## 协商变化

确定谁的交付依赖谁。双方成功互相依赖时，伙伴关系，也称 Partnership，需要共同安排重要变化、接口演进及集成。投入时间共同决定并解决交付障碍。仅有消息交换仍不足以说明这种依赖。

上游能够独立成功时，检查下游需求是否通过协商取得计划中的承诺。客户供应商协作，也称 Customer Supplier，需要约定交付内容、排期及契约验收。愿意听取请求是协商的起点。等待承诺的功能继续保持待定。

这些选择描述关系的不同方面，可以并存或演进。根据实际模型归属及协作选择，分别说明期望安排和当前安排。

## 转换结算含义

构造情景：外部提供方对成功结算和终止处理均返回 `CLOSED`，详细结果为 `SETTLED` 或 `ABORTED`。内部 `Paid` 表示已经确认款项结算。

防腐转换需要同时检查状态和详细结果：

- `CLOSED` 加已确认 `SETTLED` 映射为 `Paid`。
- `CLOSED` 加 `ABORTED` 映射为终止结果。
- `CLOSED` 缺少决定性依据时保持待确认，安排适当查询或核对。

把所有 `CLOSED` 改名为 `Paid` 会报告尚未成立的金融事实。保留解释转换所需的来源身份及证据。本地记录失败后，已确认外部结算事实保持成立，同时留下本地记录义务。

提供方控制接口，其决定约束内部消费者。双向调用及通知仍保留这种影响。下游需求进入可靠的计划过程时，描述客户供应商协作及尚待承诺内容。提供方拒绝修改时，比较遵奉模型和保留语义转换的成本。接受外部名称必须保持内部付款含义。
