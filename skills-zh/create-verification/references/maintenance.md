# 维护方法

从具体变化或已观察问题出发。恢复既有方法、判据及来源、当前产物，以及条件可能仍然适用的结果。

## 确定受影响部分

沿方法需要回答的问题追踪变化：

- 要求变化可能改变可接受结果或适用范围。
- 数据格式或协议变化可能影响输入、解析、合法变体或观察位置。
- 依赖、设备、运行环境或现场变化可能影响准备、就绪、测量或清理。
- 资料漂移可能使有效操作难以查找或使用。
- 工具缺陷可能遗漏输入、丢失观察或作出错误判定。
- 产品回归可能使可靠方法报告真实违规。

沿受影响路径选择维护范围。保留有效要求及可复用产物。证据显示变化关联其他判断时，扩大工作范围。常规运行处于既有方法范围内时，沿用原操作说明。

## 处理差异

将报告症状与判据来源、实际执行条件比较。判断变化属于已接受的新行为、方法缺陷、产品缺陷，还是条件缺失。

已接受的行为变化按其依据更新受影响判据、输入、说明或参考。方法缺陷需要修复操作或判定，并检查相关正确、错误及合法变化案例。产品缺陷需要保留失败输入和观察，再按产品任务及权限安排修复。产品插桩及其他支持性改动与其他产品工作一样，需要明确范围。

在编辑断言或参考输出前解释实际失败。保留最初的失败观察。明确接受理由后采用新基线。

## 复查变化

在受影响路径实际使用更新后的方法。需要深入检查有效性时，读取[方法有效性](./method-validation.md)。将新证据对应到更新后的对象、方法及条件。复用未变结果时，保留原生产者、版本、条件及范围。

在一个构造示例中，数据源合同将日期从本地日历日期改为 UTC 时间戳。按该决定更新解析器和时间边界案例。保留记录标识唯一这一未变要求。数据源出现重复标识时，保存违规并交给数据源维护者。改变唯一性检查需要另行决定要求。

## 更新使用入口

操作说明及引用与其描述的产物一起更新。清除被替换的当前入口，使使用者找到受支持的方法。历史证据由所属维护者保留。将改动依据、影响范围、方法检查结果及剩余条件保存到方法或所属任务中。

交付更新后的位置和操作条件。说明既有使用者需要调整什么，以及谁负责受阻部分的后续工作。持续使用为下一次维护提供依据。
