# 行为测试

有价值的断言能发现消费者可见的合理错误。确认行为、独立期望值及断言能够暴露的失败。测试范围由其保护的契约决定。

## 期望值

Oracle 是期望结果的依据，可以来自已确认需求、协议、领域规则或可独立核对的推导。把生产算法复制到测试中，可能重复同一个错误。同步修改实现及期望值也可能维持错误假设。

例如项目已确认十进制价格按分舍入，中间值向远离零的方向舍入，则 `1.005 -> 1.01`、`-1.005 -> -1.01` 及本来已经精确的值可以检验规则。用同一舍入实现生成期望值，缺少独立检查价值。

恢复需求期间，特征测试可以记录观察到的行为。明确区分当前行为及期望行为。缺失的领域规则交给项目澄清。

## 可观察行为

断言返回值、可见状态、错误、持久化结果或真实边界的消息。内部方法名及偶然调用顺序经常在保持这些保证的调整中变化。

有些交互本身就是保证，例如恰好一次扣费请求、使用缓存代替收费读取，或必要的事件顺序。可以在对应边界使用交互断言，核对请求含义及失败行为。全盘否定 mock 或调用次数断言会丢失有效覆盖。

多个断言可以描述一个结果或一个真实多步流程。将无关保证捆在一起会增加失败定位成本。测试规模由行为决定，保持案例身份及诊断信息清晰。

## 覆盖

考虑合法输入、边界、失败及状态转移。依据需要验证的语义、反馈成本及定位能力选择单元、集成或端到端检查。便宜的真实协作者可以简化测试。替身需要保持相关依赖契约。

行覆盖率帮助定位已执行及未触及的代码。它不能说明断言质量。翻转边界或丢失错误分类等具体突变，可以揭示弱断言。突变工具覆盖其选择的突变及输入。相同分数仍需进行[测试维护](./maintenance.md)中的行为及诊断比较。

## 测试先行反馈

TDD 使用失败的行为检查、足够的实现及保持行为的结构调整形成反馈。有效证据是测试确实发现目标行为的缺失，并使用可用的公共接口。工具失败或测试未被发现提供的是其他反馈。

困难的准备、过多依赖及不便调用可以暴露设计成本。先核对准备是否代表真实流程，以及隔离是否会隐藏必要语义。规则尚未确定的探索需要先学习，再建立权威期望。

测试先行及事后测试都可以保护行为。测试创建及开发节奏由当前任务安排。测试作为契约文档的价值取决于期望依据、断言及维护方式。
