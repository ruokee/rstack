# lint 设置

依据具体质量问题及误报成本选择检查和格式化设置。实际行为来自项目配置、调用方式及锁定的工具版本。读取这些依据，再判断生效结果。

## 格式化

1. 确认同一批文件由哪个 formatter 负责。已有工具先核对配置及迁移成本；初次选型比较语言支持、项目风格及工具链兼容性。锁定版本，按本页的生效范围检查实际文件及例外。
2. 区分只检查和写回命令。编辑器、提交钩子及 CI 使用一致的版本、配置和检查范围。统一格式由工具判断，审查关注配置是否符合项目约定。
3. 在临时副本制造格式差异，观察检查退出状态及差异，再写回、复查并再次格式化，确认内容稳定。格式化通过和 lint 通过分别记录。
4. 明确 lint 自动修复及 formatter 的顺序。检查冲突规则，重复执行后仍改写同一内容时，定位并调整冲突设置。保留具体例外及理由。

## 规则选择

区分格式、机械错误、语言语义及启发式维护规则。增加重复诊断前比较 formatter、编译器、类型检查器及其他 linter 的覆盖范围。

函数长度及复杂度阈值属于启发式。诊断需要结合[结构质量](../code/structure.md)中的契约及责任判断。工具严重度与审查发现的实际影响分别解释。

## 生效范围

确认命令工作目录、配置继承、覆盖、文件匹配、忽略项及工具版本。分别核对生产代码、测试、脚本及生成代码。显式文件参数的行为可能区别于目录发现。

严格度可以全局、分目录或通过明确基线采用。说明哪些文件及规则实际受检。基线是例外边界，其增长会影响保护范围。

应受检文件被跳过时，修复负责的调用方式、匹配模式或覆盖配置，再核对文件发现。将例外收窄到已确认的理由。扩大采用范围前比较诊断及维护成本。

## 例外

例外需要明确规则、最小有效范围及实际理由。生成代码的导入由生成器维护时，可以需要具体例外。广泛忽略可能隐藏理由之外的缺陷。说明抑制注释、文件排除及遗留基线如何影响覆盖。

自动修复具有不同的行为风险。依据工具分类及实际变更判断。不安全修复、扩大改写范围及批量抑制沿用任务授权。

## 自定义规则

先核对现成规则是否覆盖目标问题。项目约定明确、能机械判断且误报及维护成本可接受时，再实现缺少的检查。

1. 写明适用文件、被检查对象、例外及违规条件。语法结构适合 AST，标记间关系适合 token，独立的逐行约定适合行级检查。需要名称解析或运行时知识时，选择具备该能力的机制。
2. 定义稳定的诊断码、准确位置及可行动的消息。实现规则及其装载配置，选择实际启用的诊断，明确本地及 CI 入口。
3. 通过真实命令验证违规、合法及容易误报的边界，核对位置、消息和退出状态。与其他工具并用时划分责任，避免重复诊断。

## 验证

使用工具支持的配置展开或文件发现命令，再检查一项目标违规及其匹配的合法案例。记录生效文件、规则标识、诊断及退出状态。命令失败、文件被排除及零诊断具有不同含义。

在实际配置及文件匹配规则生效的位置使用受控临时案例。优先采用保留相关布局及配置关系的临时副本。验证实际文件发现时，使用配置适用的路径。验证完成后清理本次创建的违规案例、配对合法案例及临时配置，失败时同样清理。保留项目正式配置及获准维护的永久测试。
