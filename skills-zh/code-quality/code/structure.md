# 结构质量

代码坏味道是值得调查的症状。结构问题需要说明哪些知识、职责或依赖造成了实际成本。建议改变形状前，核对当前用法及已确认的变化。

## 长函数

检查混合抽象层次、无关的变化原因、反复解释状态及遮蔽契约的控制流。提取有价值的边界需要表达一个完整操作，拥有清楚的输入、结果及责任。

线性流程、数据表、平铺分派及必要测试准备可以较长而清晰。行数本身不足以支持拆分。让调用方重新拼装原流程的提取可能增加阅读成本。

## 重复规则

确认多个位置是否表达由同一权威维护、需要共同变化的规则。不同产品的独立策略可能暂时相同。派生表示或独立版本的契约可能更适合生成或一致性检查。

同一规则复制到多个调用方时，指出实际不一致或同步修改成本。将共同变化的规则交由其负责者维护，调用方可以共享依赖时，采用共享函数或声明式数据。独立部署的消费者可能更适合生成或明确的一致性检查，代价是增加构建或检查工作。金额和协议规则值得仔细核对一致性。类别及出现次数本身不足以决定抽象方式。

## 原始类型

字符串、数字或映射在调用方反复解释单位、区分身份、约束组合或重建合法状态时可能形成问题。包装的价值取决于正常构造及修改路径是否真正保持其含义。

核对表示能排除哪些非法状态，以及保证由编译期检查、运行期检查或使用约定建立。沿构造、修改、别名、访问及嵌套可变数据的路径检查不变量。字段赋值限制与嵌套数据的可变性需要分别判断。运行时校验由项目输入契约决定。

独立值类型能防止已确认的单位或身份混淆时采用它；枚举或记录能明确必要组合时采用相应表示。在负责构造或修改的边界维护检查。额外类型也会增加转换及接口，选择依据是实际约束的规则。

## 外部数据依赖

依恋情结表现为行为依赖其他所有者的内部结构，或重复其决策。字段访问次数只是线索。公开记录、报表、映射及纯计算可以合理地消费数据。

比较移动行为前后的依赖及调用方知识。将决策移交规则和状态的所有者，能减少内部耦合时再移动；也可提供稳定查询，只暴露调用方所需数据。移动可能把字段访问换成回调、依赖环或更大的接口。

## 变化扩散

霰弹式修改表现为同一概念的变化散落在多个所有者中，造成漏改风险。发散式变化表现为一个模块承担独立的变化原因，造成无关编辑及干扰。建议拆分或合并前先确认概念及其维护者。

协议适配、独立部署的消费者及不同存储格式可能需要多处协调变化。集中散落的共同规则可以消除漏改风险时，由同一负责者维护。拆分独立责任可以减少已确认的干扰时再拆分，使每项不变量及实施它的状态和规则保持完整归属。说明新依赖或接口成本，以及场景固有的变化。

## 薄包装

比较源契约及公开契约的合法值、单位、精度、错误分类、必要原因信息、所有权及可观察副作用。协调接口需要追踪其承诺的操作及顺序，包含部分失败及清理。

有用的命名、转换、稳定契约、生命周期、替换边界及横切行为都可以构成包装责任。只有一个底层实现时，这些责任同样可以支持保留包装。

怀疑包装只是中间人时，比较删除后每个调用方需要掌握的知识。包装增加导航及传播成本，又缺少独立责任时，可以形成间接层问题。建议移除前核对错误映射、单位、所有权及兼容性的变化。

已确认转换错误时，修复负责的映射并保持公开契约。无独立责任的转发层造成已确认导航成本时，先核对全部受影响调用方及其契约义务，再简化。深入边界设计可参考 `code-design/design-patterns/adapter.md` 或 `code-design/design-patterns/facade.md`。

## 多余机制

注册表、配置、参数和层次需要当前责任或已确认的变化依据。解释追踪、扩展或调用的具体成本。未使用的变化点造成这些成本时，优先采用满足当前契约的直接操作或依赖。保留真实消费者所需的扩展点，简化会减少预设灵活性及维护工作。

死代码判断需要入口、注册、反射及动态引用证据。注释与行为矛盾，或用于补偿可避免的结构时，可能形成维护问题。公开替代接口及必要格式重复需要核对真实消费者义务。

## 修复方向

选择能消除已确认成本的最小改动，说明保持的行为及受影响调用方。变换风险见[变更安全性](./change-safety.md)。完整替代结构可使用 code-design。
