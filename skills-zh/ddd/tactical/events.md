# 表达领域事件

领域事件，也称 Domain Event，表达已经发生且领域参与者关心的事情。选择解释决定、义务或反应所需的事实。事件可以服务同一限界上下文内部，也可以用于跨上下文集成。

## 命名事实

命令请求动作，状态记录描述当前认识，事件记录发生的事情，消息运输信息。取消命令被拒绝时，取消事实尚未成立。拒绝本身具有领域意义时，可以作为自己的事实记录。

事件提供消费者需要的含义及事实，可以包含主体身份、数量、币种、发生时间、记录时间、事件身份及权威来源。区分发生时间和本地获知时间。同一发生事实可能多次到达时采用稳定标识。

部分取消中的申请接受、履约取消确认、退款义务及退款完成具有不同含义。命名实际发生的事实。接受申请后，后续结果仍待定。用于内部计算义务的事件也是领域事件，即使它从未通过网络发送。

## 确定提交时点

领域决定可以在持久化前产生候选状态及待提交事件。由本地操作确立的事实，在成功提交后成立。回滚时丢弃该操作的待提交成功事件及对外成功声明。提交结果未知时，先查询操作的权威结果，再决定发生了什么。

以下情景具有不同结果：

- 取消被拒绝时返回拒绝结果。请求的取消尚未发生。
- 取消的本地事务失败时，该事务中的取消保持未提交。
- 取消成功提交后，确立取消事实及已记录的剩余义务。通知仍可能待发送。

按所选契约，提交前运行的事件处理器可以参与同一本地事务。在此时触发的外部效果可能逃出后续回滚范围。依据真实提交及失败含义安排这些效果。

外部事实具有自己的权威。结算提供方已确认结算、本地记录保存失败时，保留提供方已经成立的结算事实。本地记录和核对仍是义务。本地回滚无法撤销先前的外部发生事实。

## 发布契约

内部领域事件可以随模型演进。集成事件是向其他上下文公开所需事实的明确契约。把内部身份、术语及状态转换为该契约。schema 结构匹配后仍需确认业务含义一致，包括事实何时成立。

已提交事实需要可靠发布时，原子保存业务变化及发布义务，例如把 outbox 记录放在同一事务中。发布者发送已提交记录并跟踪进度。发送后、记录进度前崩溃可能造成重复。消费者需要稳定的发生标识及符合业务的重复处理契约。重复的金融效果比可重复赋值的投影需要更强保护。

解释业务所需的顺序及消费者如何理解不完整认识。消息代理投递无法独自建立外部金融效果。传输及事务的详细机制可以按需深入 `system-architecture`。

## 保留历史

事件描述发生事实。后续更正或补偿形成关联原事实的新事实。取消、撤销、退款及数据更正各有业务含义。说明消费者怎样推导当前认识。历史上曾经发生的动作保留其事实。

事件溯源，也称 Event Sourcing，以事件历史作为恢复状态的权威来源，增加事件演进、重放及历史解释责任。CQRS 区分读写模型。两者均为可选方案。使用领域事件的模型可以继续采用普通状态存储。
