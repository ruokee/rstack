# 定义聚合

聚合，也称 Aggregate，将需要受控变更边界的模型元素组织起来。聚合根提供整体身份，协调维护不变量的操作。根据真实规则及其成立时点选择边界。

## 说明不变量

对每条重要规则说明覆盖的事实、所有可能改变它的操作、允许的中间状态，以及必须成立的时刻。区分每次接受提交都需成立的规则、允许未决的流程，以及靠后续核对履行的义务。

订单可以维护自身行项目的数量规则。客户共享额度需要掌握全部已接受且尚未解除的承诺。对象图、数据库外键和共同名词各自不足以确定聚合归属。

向外部写入者提供根操作或明确领域命令。内部变化经过聚合规则。只读投影可以暴露内部事实。修改权限单独界定。引用暴露可变子对象时，解释所有允许的写入路径如何继续保护整体规则。

## 保护共享额度

构造情景：客户信用额度为固定币种的 10000 个最小货币单位，初始没有预留。订单 A、B 各请求 6000。已确认规则为已接受且尚未释放的预留总额始终不超过 10000。

各订单独立检查 `its amount <= 10000` 时，两者都通过，总额成为 12000。该检查建立单订单上限。共享额度决定需要能够掌握并决定共同承诺的领域责任。

信用账户可以负责额度及已接受预留。为每份预留赋予关联客户账户和申请订单的身份。定义 `reserve`、`release` 及其他改变承诺的操作和效果。订单记录所得预留身份及结果。账户提交边界上的预留明细和总额必须一致。

在初始账户上执行 `reserve(6000)`：

1. 读取当前权威额度及未解除承诺。
2. 判断新增预留是否符合额度。
3. 在维持决定前提的条件下，原子保存已接受承诺及受影响账户事实。
4. 操作提交后才报告已接受。

A、B 都读取版本 0 时，条件提交可以让 A 预留 6000 并推进账户版本。B 的版本 0 提交发生冲突。B 必须根据当前事实重新作领域决定；可用额度为 4000，其 6000 请求因额度不足而拒绝。相反顺序得到对称结果。

使用已接受的过期决定重试持久化会重复错误。明确选择冲突结果。调用方可以收到冲突，也可以按操作契约安排重新决定。

## 区分责任层次

领域函数或方法根据传入状态作决定。竞争写入需要条件更新、版本比较、合适的锁，或具备相应隔离及写入条件的事务来保护共享事实。单独标注事务仍未说明并发性质。

所有改变承诺的路径都必须参与所选机制，包括释放预留和调整额度。说明保证范围，声称持久化正确性时检查真实机制。本地检查之后，其他进程仍可能持有旧快照。

业务允许分配有限额度份额时，可以考虑分配模型。它需要保证分配总额受限并保持各份额权威的规则。本情景由一个账户作共同决定即可满足要求。

## 选择合适大小

过大的聚合增加加载成本、争用及修改耦合。过小的聚合会把即时不变量拆散到独立决定中。按规则和真实访问路径选择。子记录可以分别存储，并参加同一个受保护操作。

业务允许中间状态时，跨聚合流程使用未决工作及明确协调。真实规则要求原子变化时，比较调整聚合边界和采用合适事务或协调机制的方案，说明代价。聚合边界和部署单元各有用途。

部分取消情景中的 `shipped + confirmedCancelled <= ordered` 必须经受发货确认与取消确认的竞争。使用这些数量的当前权威，在同一批商品上保护决定。申请接受后记录待处理工作，直至履约方确立取消事实。
