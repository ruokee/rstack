# 映射上下文关系

上下文图，也称 Context Map，解释现有模型怎样接触、互相影响，并通过真实协作演进。提出变化前先识别各模型及适用范围。分别标明现有安排和提议安排。

## 描述关系

对每个接触点记录双方模型、交换信息、身份关联、语义转换、影响方向、变更协商及集成负责者。使用图时，解释箭头方向或标签的含义。

上游影响表示一方的模型或开发决定约束另一方的成功。数据可以同时双向流动。HTTP 调用方向、事件发布和业务影响回答不同问题。交付相互依赖时，即使技术数据只向一方流动，也可能需要合作。

## 选择协作方式

### Partnership

伙伴关系表示双方各自依赖另一方交付成功。协调重要计划、接口演进及集成。共同成功需要投入时间共同决定并解决交付障碍。两个系统交换消息本身不足以确定这种关系。

### Shared Kernel

共享内核表示双方明确共享有限的领域模型及关联实现或 schema，共同控制变化。范围保持可理解，通过整合维持含义一致。代价是紧密协作和耦合演进。共享日志或 HTTP 工具库属于普通技术复用。

### Customer Supplier

客户供应商关系表示下游需求通过真实协商及承诺机制进入上游计划。约定交付内容、排期和契约验收。上游在其他方面可以独立成功。愿意听取请求使协商成为可能，尚未承诺的功能保持待定。

### Conformist

遵奉表示下游在适用范围接受上游模型。这减少转换，也让上游控制重要表达及演进。维护独立模型收益很小时，这种选择可以合理。检查采用上游模型是否保留了下游真实规则。

### Anticorruption Layer

防腐层让下游以自己的领域模型表达上游能力。转换含义、身份、单位、状态，以及失败或信息缺失情况。代价是随双方模型变化维护语义映射。它可以与合作型上游关系并存。

传输适配器处理连接及表示细节。防腐层通过保护含义承担领域职责。责任明确时，一个实现可以同时完成两项工作。

### Open-host Service

开放主机服务由上游向多个消费者提供明确协议，维护连贯的共同契约及演进。单个消费者的特殊需求可以使用专用转换，以保持共同契约。API 的存在尚未说明开放程度及预期消费者范围。

### Published Language

发布语言让参与者用有明确文档及共同含义的语言交换信息，按需与内部模型转换。它可以采用行业标准或项目契约。代价包括 schema 维护及语义演进。共享 schema 仍需对字段含义达成一致。

### Separate Ways

各行其道表示集成收益低于成本时保持上下文独立。计入实际重复工作或人工衔接成本。必要义务在其执行位置仍需负责者。

### Big Ball of Mud

大泥球标明模型和规则混杂、内部边界不一致的既有区域。描述已知接触点，按需隔离其影响。这记录真实情况。整体重写需要自己的理由及授权。

模式可以组合并演进。根据实际协作及模型决定选择。希望发生的变化与当前关系分别说明。

## 转换结算含义

构造情景：外部提供方对成功结算和终止处理均返回 `CLOSED`，详细结果为 `SETTLED` 或 `ABORTED`。内部 `Paid` 表示已经确认款项结算。

防腐转换需要同时检查状态和详细结果：

- `CLOSED` 加已确认 `SETTLED` 映射为 `Paid`。
- `CLOSED` 加 `ABORTED` 映射为终止结果。
- `CLOSED` 缺少决定性依据时保持待确认，安排适当查询或核对。

把所有 `CLOSED` 改名为 `Paid` 会报告尚未成立的金融事实。保留解释转换所需的来源身份及证据。本地记录失败后，已确认外部结算事实保持成立，同时留下本地记录义务。

提供方控制接口，其决定约束内部消费者。双向调用及通知仍保留这种影响。下游需求进入可靠的计划过程时，描述客户供应商协作及尚待承诺内容。提供方拒绝修改时，比较遵奉模型和保留语义转换的成本。接受外部名称必须保持内部付款含义。
