# 事件驱动设计

事件记录或宣布事实，例如 `OrderPaid`。消费者按约定的 schema 和投递机制响应。这将生产者操作与响应实现分开，同时引入投递、时机及失败契约。

## 定义消息

命令请求操作，例如 `ChargeCard`。事件描述观察到的结果，例如 `PaymentCaptured`。通知可以携带事实，也可以要求消费者读取当前状态。后一种情况下，稍后的读取可能看到更新版本。

含义和路由是不同选择。事件可以只有一个消费者，多个 worker 也可以竞争执行命令。必需的事件响应仍是真实依赖。操作承诺某项响应已经完成时，其所有者需要取得完成依据。

定义载荷含义、身份、相关版本，以及它保存事件发生时的数据，还是指向当前数据的引用。消费者需要不同 schema 版本时，应安排兼容演进或迁移。

## 选择投递语义

- 同步分发在返回前运行处理器。明确顺序、重入，以及失败时停止后续处理器还是收集错误。较早的效果可能已经完成。
- 进程内异步分发将工作交给有明确归属的任务或队列。定义容量、任务归属、失败报告及关闭行为。仅存于内存的消息会在进程终止时丢失。
- 持久化传输在自己的边界内定义持久化、确认、保留、顺序及重新投递。明确发布成功或确认具体代表什么。

入队确认与业务效果完成是不同节点。顺序可能只对某个键或分区成立。并发消费者的完成顺序可能不同于投递顺序。将所需顺序落实到实际执行机制。

## 协调持久化

数据库提交前发布，可能暴露随后被回滚的事实。提交后发布，则存在进程在发布前停止的间隙。需求将存储状态与最终投递关联时，outbox 可以在同一事务中记录状态变更及消息，再由独立所有者负责投递。

outbox 仍需要处理投递失败及重复。需要该原子边界时再采用它。直接调用或本地[观察者](../design-patterns/observer.md)可以满足进程内响应。

## 在效果边界处理重复

至多一次投递允许丢失，至少一次投递允许重复。精确一次声明需要明确边界及故障模型。消息代理事务不会自动包含外部扣款或邮件。

根据操作选择幂等效果、去重或事务协调。去重标记与数据库变更必须共同成功时，将它们原子提交。单独的先读后写检查会与其他消费者竞争。去重键、保留期限，以及同键不同内容的处理影响正确性时，应明确约定。

必需的重试需要所有者、停止条件及持续失败的处理方式。死信队列将失败工作保留给明确的后续处理流程。它不会完成该工作。保留足够的操作上下文，将消费者失败关联到原因。

## 负责生命周期

说明何时停止接收工作、怎样排空或放弃排队内容，以及何时等待活动处理器完成清理。跟踪超出有效作用域的订阅及注册。用实际工作量和队列上限约束事件级联，检查可能无限生成事件的反馈循环。

事件溯源将事件序列作为权威状态历史，需要承担事件演进、重放及投影一致性责任。普通事件发布可以与仍作为权威来源的数据库共存。重放历史事件时，需要明确外部副作用策略。

独立响应、扩展点及受益于分离投递的工作流适合采用此方法。直接顺序能更清楚表达控制流和完成契约时，保留直接顺序。重复输入参见[状态机](./state-machine.md)，任务及队列上限参见[异步并发](./async-concurrency.md)。
