# 既有代码

通过调整结构，让具体操作或变化更容易处理。从受影响的调用方和规则开始，在所选迁移过程中保持要求中的可观察行为。

## 确认代价

追踪已报告困难或真实的近期变化，寻找同一规则的重复解释、调用方对内部结构的依赖、归属冲突的状态，以及集中经过一个模块的无关变化。记录相关行为及当前结构迫使调用方承担的工作。

行数、文件跳转及模式名称是调查线索。调整边界的依据是它对正确性、调用知识、运行成本，或已有证据支持的后续修改范围的影响。

## 区分契约

描述所需输入、输出、顺序、错误、部分效果及资源行为，区分预期行为、兼容义务和已知缺陷。结构重构保持其行为契约。有意纠错需要明确改变该契约。

确认要求在哪里实施，以及哪些调用方依赖它们。内部类型可以在私有范围内维护重要不变量。公开方法也可能暴露项目无需保留的偶然行为。

## 追踪依赖责任

对受影响依赖明确契约归属、生命周期、失败行为及替换代价。分开策略和机制能够减少变化传播时，再进行分离。

- 进程内代码可以拥有独立规则和资源。共享进程不足以成为合并职责的理由。
- 远程依赖带来部分失败、延迟及独立变化的状态，同一团队拥有它也适用。
- 第三方接口可能需要转换成调用方概念。有意成为产品一部分的公开协议细节应予以保留。
- 测试替身需要表达所检查的语义，尤其是并发、事务行为及清理。降低准备成本可以说明替换点的价值。

根据[接口](./interfaces.md)写出拟议调用用法，说明哪些现有工作移到边界内部，以及之后由谁负责。按实际困难比较保留原结构、移除间接层或增加边界。

## 保持变化完整

将一条规则及其约束一起迁移。例如，配置解析产生语法值，统一解释步骤应用默认值和优先级，执行阶段使用最终设置。各调用方应明确自己拿到的是哪种表示。

移动代码时保留独立生命周期和一致性边界。把可变状态复制到新模块可能产生第二个权威来源。把查询藏到辅助函数后面可能掩盖重复 I/O。沿调用方的完整操作检查这些影响。

## 完成迁移

列出受影响的生产方、消费方、构造路径、持久化格式及文档，选择能保持有效中间状态的切换顺序。所有使用方共同迁移时，一次协调替换可能更简单。独立发布的使用方可能需要明确的兼容期。

迁移所选切换范围内的全部使用方，移除过时路径。兼容路径需要真实义务及退出条件。调整检查时保留独特的行为覆盖。仅约束废弃内部形状的断言应随该形状移除。

改动后运行相同的代表性操作，包含促成该边界的失败路径，检查可观察结果、资源行为及相关成本。反复需要为拟议设计添加例外时，应重审其假设。
