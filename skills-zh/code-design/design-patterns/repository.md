# 仓储

仓储通过类似集合的契约，提供面向领域的持久化实体或聚合访问，集中维护调用方不应重复处理的映射及访问决定。存储语义影响正确使用时，仍需成为契约的一部分。

## 定义调用方所需操作

说明身份、记录缺失行为、排序、过滤、分页及返回状态，区分独立快照、被跟踪对象和绑定会话的值。定义加载何时执行 I/O，以及访问关联是否会发起额外查询。

例如，预留操作需要当前可用量，并在竞争写入下执行原子更新。返回可变库存快照不能让之后的保存自动正确。带预期版本的条件更新，或合适的事务及锁，可以维护所需规则。

完整加载聚合会浪费工作时，报表可以使用查询专属投影。让调用方的批量操作可见，便于实现避免逐项重复查询。

## 选择隐藏内容

仓储可以隐藏行映射和面向领域的查询。公开厂商查询构建器、ORM session 或懒集合，会保留公开依赖。调用方需要该查询模型时，可以有意选择它。

小型数据访问操作可以直接使用 SQL 或现成 ORM 接口。仓储拥有有意义的领域契约或访问策略时才有价值。一个存储实现也可以足够。假想的数据库替换是薄弱理由。

## 安排事务归属

多个仓储操作必须共同提交时，让它们共享事务范围及完成所有者。内部提交会提前终止这种协调。仓储操作本身就是完整原子操作时，可以由它拥有事务。

在 API 中明确提交归属，并说明嵌套使用方式。协调变更跟踪及完成参见[工作单元](./unit-of-work.md)。

## 验证存储语义

通过真实实现检查约束、查询结果、更新冲突、加载行为及事务结果。内存替身可以支持纯策略检查。它的排序、隔离、身份及失败行为可能不同。

针对代表性调用操作测量查询数量和传输数据量。清楚的方法名仍可能隐藏无界扫描或 N+1 查询。

由策略拥有持久化契约时参见[依赖倒置](../design-principles/dependency-inversion.md)。[外观](./facade.md)可以协调仓储及其他依赖上的完整用例。
