# 外观

外观提供子系统的一项完整操作，负责有用的协调，让调用方表达意图，避免重建内部步骤。它可以是函数、模块，或共享子系统依赖的对象。

## 明确协调用法

说明调用方希望完成什么，以及哪些步骤必须配合。开票操作可能需要加载数据、创建发票及安排通知。外观可以负责顺序、结果组装及部分失败契约。领域规则仍归权威所有者维护。

经过选择的包 API 也可以充当外观，其价值取决于隐藏的决定和义务。单次委托调用仍可以承担有效的兼容或生命周期边界。

## 定义部分完成

假设操作先提交发票，再发布事件。发布失败时，发票已经存在。不区分状态的失败结果，可能导致调用方重复操作并创建第二张发票。

按用例实际需要选择契约：

- 用发票标识及通知结果表达部分完成，定义调用方怎样从该状态继续。
- 创建发票必须持久安排通知时，在同一个受支持事务中写入发票及 outbox 条目。成功表示发票和发布意图均已提交。实际投递遵循独立的发布者契约。
- 调用方需要控制事务或发布时间时，在合适的下层公开操作，并明确归属。

存储契约报告提交结果未知时，需要保留该状态。外观的名称不能将独立效果变成原子操作。参见[工作单元](./unit-of-work.md)及[事件驱动](../approaches/event-driven.md)。

## 保留所需控制

调用方需要分页、取消、批处理或有意义的错误分类时，应保留这些能力。为真实的进阶用法提供下层操作，并在所有受支持路径维护不变量。直接访问是一项产品决定。它不自动授予绕过协调的能力。

避免仅因共享基础设施，就把无关用例积累到一个对象中。共享依赖可以统一组装，各项操作仍保留自身契约。

## 区分相邻模式

[适配器](./adapter.md)转换既有契约，外观组织有用的高层操作。中介者协调参与者之间的通信，参与者通过它回调。外观通常单向组织子系统用法，内部部件可以独立于该入口运行。

根据[深模块](../design-principles/deep-modules.md)判断调用知识及公开的失败成本。
