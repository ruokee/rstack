# 状态模式

GoF 状态模式将依赖状态的操作委托给当前状态对象。上下文拥有持续交互及公共数据，各具体状态实现状态契约。替换活动状态后，后续请求的行为随之改变。

## 从状态模型开始

根据[状态机](../approaches/state-machine.md)定义合法状态、事件、守卫、转移及失败结果，再选择行为组织方式。状态对象、枚举匹配、转换表及归约器，都是该模型的可选实现。

多个操作在各状态具有较多专属行为时，多态状态对象可能适合。例如，连接在握手、打开或排空阶段，可以分别处理发送、接收及关闭。将各阶段的相关行为放在一起，可能比在多个操作中重复阶段检查更清楚。

## 安排转移责任

选择由状态计算后继状态，还是由上下文决定。状态可以返回转移结果，再由上下文应用。这样可以控制上下文修改，同时让状态专属决策保持局部。

说明效果与状态变化的先后关系，以及失败后留下什么。进入状态可能获取资源，离开状态可能需要显式完成。单独替换对象引用不能提供这些语义。

状态内部的转移让行为接近其条件，也可能将转换图分散到多个文件。集中转换表提供统一的允许转移检查位置。按实际操作比较这些成本。

## 管理状态数据

区分上下文公共数据和仅在某状态存在的数据。行为及捕获依赖允许时，可以共享无状态的状态实例。实例专属状态和资源需要明确生命周期。

Rust trait object 支持运行时状态实现，并增加动态分发。所有权可能让借用状态的替换更复杂。状态方法返回转移结果，或采用枚举，都可以简化它。封闭枚举还支持穷尽匹配。类型状态可以在编译时限制可用操作，同时增加动态存储及条件转移的复杂度。

## 选择较小表示

状态主要改变返回结果或转移许可时，可以使用分支或表。为简单转发增加状态类，会无谓地分散一个小操作。可扩展状态对象可以让新实现保持局部。通向它的转移和共同契约仍可能需要修改。

[策略](./strategy.md)改变操作选用的算法，状态模式按生命周期及转移规则组织行为。[命令](./command.md)可以表示触发转移的请求，或由转移安排的后续效果。
