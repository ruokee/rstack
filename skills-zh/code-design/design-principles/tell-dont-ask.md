# 告诉而非询问

Tell Don't Ask 将改变状态的决策放在能够维护不变量的所有者处。调用方请求执行操作，避免根据公开字段重建规则。规则及其实施责任因此集中维护。

## 在更新处维护规则

账户扣款需要检查可用余额、检查冻结、扣减余额及记录扣款，这些步骤属于一项明确操作。各调用方应获得成功或拒绝结果。分开读取再修改公开字段，会让调用方遗漏步骤，并与其他写入者竞争。

对象方法可以维护其独占控制状态的规则。持久化余额需要存储更新实施相应并发条件。仅将检查移入方法，仍然保留先读后写的竞争。

检查全部修改路径。私有表示及受控操作可以让调用方遵守契约。公开 setter 或可独立修改的副本可能绕过该控制。

## 保留有效查询

报表、渲染、序列化及读模型需要数据。向这些使用方提供合适的值或快照，并说明新鲜度。底层状态存在不变量时，查询仍然有用。

纯函数也可以根据显式输入计算决策。效果所有者需要在应用时确认输入仍然适用，或通过事务、版本检查建立该条件。参见[函数式核心](../approaches/functional-core.md)。

## 选择合适规模

批量操作可以对多条记录实施同一规则，同时避免每个对象发起一次远程调用。将规则交给能够满足所需规模及一致性范围的权威来源。对象位置接近并不足够。

让昂贵查询和副作用在 API 中可见。意外触发 I/O 的属性会隐藏调用方需要控制的成本。由另一所有者执行业务操作时，数据传输记录可以保持透明。

选择所有者参见 [GRASP](./grasp.md)，受控状态操作参见[面向对象](../approaches/object-oriented.md)。
