# 保持简单

KISS 倾向于满足实际契约的最简单设计。需要衡量的是使用、理解及修改它所需的概念和义务。简短源码仍可能隐藏昂贵工作或复杂控制流。

## 定位复杂度

部分复杂度来自问题本身，例如合法状态、竞争更新、部分失败或真实协议。设计需要在适当位置表达它们。额外复杂度来自多余状态、重复解释、假想选项，或没有当前职责的间接层。

沿完整操作比较成本。迫使每个使用方配置生命周期的简短调用，可能比显式所有者更复杂。较长的顺序函数，可能比许多依赖隐藏共享状态的辅助函数更易理解。单个实现也可以通过接口承担真实转换或兼容边界。

## 优先直接机制

固定映射使用查表，小规模封闭选择使用分支，无状态计算使用函数。让长期状态和资源具有可见归属。选择能直接表达所需保证的语言及库机制。

例如，将三个外部字段名映射为内部名称，通常只需映射表或直接构造。插件注册表增加发现、注册顺序及缺失实现的处理义务。这些义务需要真实扩展要求。

## 比较总成本

检查调用知识、可变状态、控制流、依赖数量及变化传播，按情况纳入分配、复制、重复 I/O 和任务保留成本。避免用每个调用方都必须配置的通用框架，替代清楚的局部操作。

正确性和所需性能仍是简单设计的目标。操作需要清理、失败报告及同步时，这些机制就有价值。将必要优化放在受影响行为附近，说明它成立的条件。

通过[深模块](./deep-modules.md)容纳必要复杂度。假想能力参见 [YAGNI](./yagni.md)。减少重复却增加耦合时参见 [DRY](./dry.md)。
