# 依赖倒置

依赖倒置让策略所需契约独立于实现该契约的细节，再让细节依赖契约。这样可以容纳厂商、存储或传输变化，让策略继续使用自身概念表达。

## 区分设计决定

- 依赖倒置关注谁定义抽象，以及哪些源码依赖它。
- 依赖注入从使用方外部提供依赖。
- [适配器](../design-patterns/adapter.md)将既有契约转换为所需契约。
- 分发决定怎样选择或调用具体实现。

注入厂商专属客户端，仍可能让策略依赖厂商概念。适配器可以转换接口，同时让两侧接口都归基础设施所有。泛型参数可以用静态分发实现依赖倒置。

## 定义所需契约

表达策略实际需要的操作，包含错误、部分结果、归属及一致性要求。避免给整套厂商 API 改名后直接复制。库存预留的正确性依赖并发库存时，需要原子预留操作。拆开的读取和写入方法会把该责任留给调用方。

策略需要值时，直接传值。只需一个时间戳的计算可以接收该时间戳。长期操作需要在多处观察新时间时，才可能需要时钟能力。区别来自用法和生命周期。

在 Rust 中，trait bound 可以表达能力。它无需采用 trait object 或堆分配。借用的 `dyn Trait` 动态选择行为并借用实现。Python 的 callable 或 protocol 可以表达相同依赖角色。两种语言的静态和运行时保证各不相同。

## 在归属处组装

在配置及生命周期已知的位置创建具体依赖，再交给使用方。组合根可以是应用启动位置，也可以是带作用域的操作。它还决定关闭顺序及哪些依赖共享。

显式参数通常能让对象关系可见。容器可以管理确有变化的作用域或组装。全局服务定位器把依赖发现放进隐藏查找，使构造和失败更难追踪。

## 保持边界价值

稳定纯函数和语言库操作通常可以直接依赖。边界应承载真实策略、转换、生命周期、变化或有用的隔离要求。判断实际职责，避免按实现数量决定结构。

用于验证的替身需要保留当前检查所依赖的语义。内存存储的锁、事务隔离及失败行为可能不同。出现深层 patch 时，应同时检查生产边界和测试假设。
