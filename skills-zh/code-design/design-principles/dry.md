# DRY

Hunt 和 Thomas 在《程序员修炼之道》中将 DRY 表述为："每一条知识在系统中必须拥有单一、明确、权威的表示。"关注点是持续一致地维护同一个决定。相似文本可以表达互不相关的决定。

## 确认共同规则

询问每处实现对应什么要求、由谁负责，以及哪些变化必须覆盖全部位置。开票和结算中的金额舍入可能表达同一会计规则。两个独立管理的产品中，相似校验可能由不同主体负责，发布节奏也不同。

区分重复的权威来源和派生表示。生成的客户端、缓存值及物化视图可以合理地重复信息。其来源、更新机制及新鲜度契约决定是否会失去一致性。独立编写的预期结果可以用于验证规则。

## 选择一致性方法

- 使用方可以遵守同一契约时，用一个操作承载共享计算或不变量。
- 不同语言或部署单位需要独立产物时，从权威 schema 生成表示。
- 使用方独立版本化时，定义版本契约并检查兼容性。单独共享库仍允许已部署版本存在差异。
- 数据存在副本或缓存时，说明谁修改权威来源，以及派生状态怎样追上变化。

风险越高，越需要明确权威来源及验证。风险本身不能决定采用运行时服务、共享包或共同继承树。选择时需要考虑发布耦合、可用性、延迟及归属。

## 避免错误共性

独立变化的规则应分别维护，即使当前实现相同。辅助函数需要针对调用方的标志和例外时，可能混合了不同职责。按职责拆分能够降低正确修改的成本时，再进行拆分。

例如，客户折扣和员工福利当前都可以减免百分之十。将它们合并，会让一项政策的变化影响另一项。两者遵循同一金额契约时，仍可以共享舍入操作。

共性不明确时参见[三的原则](./rule-of-three.md)。用[深模块](./deep-modules.md)判断共同操作是否减少调用知识，用 [KISS](./kiss.md) 比较结构成本。
