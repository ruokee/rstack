# SOLID

SOLID 汇集了与 Robert C. Martin 相关的五项面向对象设计原则，用于检查职责、行为契约和依赖方向。这些问题也适用于函数及模块。实现机制由目标语言决定。

## 单一职责

将因同一原因变化的行为放在一起。不同要求控制的规则放在一起会互相干扰时，应将它们分开。内聚性比类或函数包含多少操作更重要。

例如，发票计算、文档排版和存储格式可以独立变化，各自拥有契约，再由一个用例操作协调。把每一步算术都拆成对象，会分散计算职责。

检查近期修改涉及哪条规则，以及影响传播了多远。协调多个步骤的模块仍然可以具有一项完整职责。

## 开闭原则

围绕已知变化方向保护稳定操作。扩展机制固定一份契约，让新实现遵循它。其价值取决于契约稳定性，以及修改既有使用方的成本。

封闭枚举和穷尽匹配显式表达已知变体集合，新增变体时，受影响的匹配需要重新处理。可扩展接口允许新实现提供行为，而各使用方继续遵守原有契约。选择取决于变体和操作中，哪一方需要独立变化。

按实际变化及语言机制选择函数参数、泛型参数、trait、protocol、注册表或配置。插件协议需要实际扩展义务。实现数量不足以证明该义务成立。参见 [YAGNI](./yagni.md)。

## 里氏替换

行为可替换性要求实现遵守使用方收到的契约，接受承诺的输入域，维护不变量和允许的状态历史，提供承诺的结果及失败行为。子类型不得加强前置条件或削弱后置条件。

例如，只读集合无法通过提供一个总会失败的修改方法，满足承诺修改能力的接口。允许部分写入的写入器符合部分写入契约。它不符合成功即表示全部写入完成的契约。

类型兼容性只检查类型系统表达的性质。时序、资源归属、错误含义及别名行为需要明确契约和相应检查。复用实现和承诺可替换性是两项不同决定，参见[组合优于继承](./composition-over-inheritance.md)。

## 接口隔离

描述使用方实际需要的能力。记录读取方应能依赖读取能力，而无需承担事务管理或删除职责。使用方及义务不同时，再拆分接口。

选择最小且完整的能力。无需为每个方法单独建立接口。共享会话、不变量或生命周期的操作可能需要放在一起。过多独立接口会掩盖这种关系，增加组装负担。

callable 可以表达单项操作，trait 或 protocol 可以表达相关能力。稳定的内部协作仍可以使用具体参数类型。

## 依赖倒置

由策略定义它需要细节满足的契约，再让细节实现该契约，使细节变化留在策略边界之后。运行时调用仍可以从策略流向细节，源码依赖则指向策略所需契约。

从外部传入具体厂商客户端属于依赖注入。转换其响应属于适配。任一动作都不足以决定抽象归属。契约归属及组装参见[依赖倒置](./dependency-inversion.md)。

## 综合判断

沿完整操作作出判断。拆分职责可能增加协调。扩展接口可能削弱穷尽检查。窄能力可能增加共享生命周期的管理难度。抽象可能按具体表示增加分发及分配成本。

选择能维护所需行为、额外知识和机制最少的结构。用 [GRASP](./grasp.md) 安排职责，用 [KISS](./kiss.md) 比较总体复杂度。
