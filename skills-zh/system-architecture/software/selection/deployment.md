# 部署

选择满足应用发布、资源、隔离、扩缩及恢复要求的运行模型。按[架构决定](../../core/decisions.md)纳入现有安排及实际运维成本。

## 分配运维责任

追踪构建、产物保存、配置、部署、健康检查、流量准入、扩缩、观察、事故响应及恢复。对各相关义务明确由应用团队、平台团队或提供方执行。补丁、升级、持久存储、备份及还原按其系统归属纳入。

定义所需隔离边界。进程、容器、虚拟机、物理主机、账号及区域具有不同故障和资源共享特性。按要求核对所选平台实际保证。

## 比较运行模型

主机或虚拟机上的进程提供直接运行时及放置控制。其他服务明确提供能力之前，负责人承担进程监督、发布、容量、主机更新及恢复。

托管应用服务把指定平台工作交给提供方，需要比较支持的运行时、网络、配额、部署行为、持久化、观察、恢复及退出。责任按服务契约分配。

容器打包执行依赖，可以让发布产物可重复，同时增加镜像维护及运行配置。容器打包之外，调度、服务可用、持久数据及发布归属取决于所选运行安排。托管容器服务可以承担部分责任。

Serverless 服务可以提供事件触发执行及按需容量。按所选服务核对并发、启动行为、执行时长、内存、网络、投递语义及价格。长操作需要兼容的执行模型或持久协调模型。持续负载可能改变成本比较。

Kubernetes 等编排平台通过声明状态提供工作负载调度及调节，可以在配置机制下支持独立发布、资源策略、发现及恢复。运维方承担控制面或提供方关系、集群升级、网络、存储集成及事故处置能力。托管集群会改变这项分工。

## 设计发布

健康检查需要反映实例是否应接收流量。平台区分启动、就绪及存活时，分别说明用途。定义排空、在途操作、配置版本，以及坏版本发布时持久效果的去向。

滚动、蓝绿、金丝雀及完整替换具有不同容量和兼容要求。把流量转回旧代码需要兼容状态。结构及权威过渡见[软件迁移](../migration.md)。版本化基础设施声明可以支持重建和审查，实际恢复还需要数据及可用依赖。

## 按要求改变选择

构造情景：少量服务采用托管部署，已经满足发布、可用及容量目标。保留当前安排可以避免另一平台的运维负担。编排需要具体收益覆盖采用、支持及退出成本。

变体：同一小系统新增明确租户隔离要求，以及当前服务无法提供的独立发布协调要求。按这些要求比较更强的托管服务、独立环境及编排平台。编排能以可接受责任提供所需保证时，少量服务也可以采用。

记录触发重审的未达目标及运维负责人。服务数量或项目年龄本身会留下选择问题。观察信号见[可观测性](./observability.md)。
