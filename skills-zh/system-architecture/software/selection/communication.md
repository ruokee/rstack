# 通信

先选择交互契约，再选择协议。明确调用方需要知道什么、何时取得结果，以及谁负责未完成工作。按[架构决定](../../core/decisions.md)比较可行方案。

## 定义交互

同步请求响应让调用方等待结果，完成时间及可用性会依赖对端。对端执行后超时可能留下未知结果。确认也可能只表示受理，后续异步执行。

异步交互分开受理及完成，需要定义持久受理、操作标识、待定状态、结果获取、失败归属及最晚有效完成时间。队列可以吸收突发，持续过载仍需要容量或准入决定。投递及重复效果见[消息](./messaging.md)和[一致性](../consistency.md)。

流式交互暴露连续结果或进度，需要定义分帧、顺序、背压、连接期限及断开含义。契约承诺恢复时，需要游标或等价的可恢复状态。显示部分回答及完成业务动作是两个结果。

## 比较协议

- REST 风格 HTTP 接口通过广泛支持的客户端、中间设施及调试工具暴露资源和操作。类型结构及生成客户端可以提供显式契约。按负载评估表示、缓存、请求大小及性能。
- RPC 提供具名操作及结构化契约。gRPC 等系统提供 IDL、代码生成及流式能力，部署及客户端支持取决于传输方式和版本。直接比较浏览器、代理、外部客户端及运维要求。
- GraphQL 让客户端按结构选择字段，可以减少客户端专属聚合，把查询规划、字段授权、成本核算及解析器效率放到服务端。修改操作仍需要准确的业务效果契约。
- Webhook 向回调地址投递通知，需要明确事件标识、确认、重复投递、顺序及遗漏事件恢复。收到通知及通知所述业务事件各有含义。身份及信任要求取自实际集成。
- MCP 等 Agent 工具协议暴露工具、资源及上下文，提供交互格式。应用继续负责业务授权、工具效果及恢复。核对所选协议版本及宿主能力。

## 补齐边界契约

定义字段含义、必要值、单位、错误、截止时间、取消、重复处理、版本兼容、配额及结果保存。可能出现时，分别表示执行前拒绝、已知失败、完成成功及未知结果。说明哪些错误允许重复，以及对应的效果保证。

取消可能停止等待、排队工作或正在执行的工作，需要指明支持哪层，以及已提交效果怎样处理。超时预算属于整个调用方可见操作，包括扇出及重试。见[韧性](../resilience.md)。

公开接口兼容性依赖消费者行为，包括严格解析及生成客户端。看似新增的变化也要按实际契约核对。内部调用方无法同时更新时，同样需要发布协调。

构造情景：退款工具向提供方提交后超时。REST 改成 RPC 仍会留下不确定性。稳定操作标识、提供方契约、可查询状态及明确恢复负责人决定安全的后续动作。
