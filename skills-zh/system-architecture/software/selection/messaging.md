# 消息

按保留信息的角色选择，包括可重建缓存、待执行工作或事实流。同一产品可以在不同配置及保证下承担多个角色。按[架构决定](../../core/decisions.md)比较候选。

## 选择缓存

缓存保留派生结果，减少重复工作。本地缓存避免网络调用，各进程承担自身新鲜度及内存义务。分布式缓存共享结果，同时增加网络及服务依赖。CDN 把适合内容放到读者附近，需要键、失效及内容访问规则。

明确权威、键作用域、过期、失效、刷新并发及缓存丢失后的结果。常用于缓存的产品也可以在另一持久化契约下保管权威状态，按实际角色称呼它。旧值填回及重建压力见[数据权威](../data.md)和[容量](../scaling.md)。

## 选择队列

任务队列分开接受及执行。明确持久接收确认承诺什么，以及客户端怎样取得完成结果。它可以吸收突发，让工作者恢复未完成工作。持续能力缺口仍会增加积压。

比较生产确认及持久化、复制失效行为、消费租约或可见窗口、确认时机、重复投递、顺序、过期及死信处理。副作用后、确认前崩溃可能重复效果。消费者重复安全性按[一致性](../consistency.md)判断。

构造情景：工作者退出后，已接收的文档处理任务仍在队列。恢复后需要足够能力处理新流入，并在承诺窗口前清空积压。即使队列数量下降，最老任务年龄仍可能暴露违约。

## 选择事实流

命令要求参与者执行操作，事件报告已发生的事。保留日志在保存契约内支持重放及独立订阅位置。发布订阅提供逻辑订阅扇出，同一组内消费者可以分摊该组工作。

明确事件标识及含义、结构演进、顺序键、分区、重放期限，以及迟到或重复事实的处理。效果边界缺少防重机制时，重放通知事件可能再次发送通知。必要审计历史需要对应的完整性及保存契约。

分区内顺序会留下跨分区顺序问题。确认可能表示消息系统接收、持久复制或消费者完成，需指明具体一种。端到端操作可能跨越多个这样的边界。

## 比较运维契约

按所需语义比较保留日志、路由任务队列、轻量通道及托管服务。托管把消息设施维护交给提供方，消费者继续承担配额、积压、投递语义、事故处置及退出责任。

核对所选产品版本的持久化、事务范围、限制、顺序、保存及恢复。计入人员及保留数据的重放、迁移费用。操作同时要求业务提交及发布时，用合适的事务或可恢复机制连接它们，例如 Outbox。投递及外部效果限制见[一致性](../consistency.md)。
