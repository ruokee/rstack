# 系统结构

按改变的关系、解决的问题及增加的代价比较结构形式。不同形式可以组合。领域含义、代码组织、运行隔离、部署及团队归属分别判断边界。

## 比较结构

- 分层分开关注点并控制依赖方向，例如表现、领域规则及持久化。这些关注点分别变化时，分层可以限制影响。只传递数据的层增加阅读及转换开销。各层可以位于同一进程。
- 模块化单体共同部署，内部保持明确责任及访问规则。本地调用及事务减少分布式协调，发布及进程资源仍然共享。按模块扩容或隔离崩溃需要另外的运行边界。
- 服务可以提供独立发布、资源扩展、故障隔离或归属。契约需要保留所需独立性，代价是网络延迟、部分失败、数据协调、发现及运维。小团队也可能需要隔离，大团队仍可以共享部署。按所需机制及实际运维能力判断。
- 事件驱动发布事实供下游响应，可以减少生产者对消费者的了解，支持独立反应。事件含义、去重、顺序、新鲜度及恢复成为契约。命令要求执行动作，事件报告已发生的事。沿两者追踪业务操作。
- 队列分开接收及执行，在其持久化契约内可以让工作跨越消费者故障。它支持长任务及短期突发，同时需要面向用户的受理及进度语义、面向运维的积压及重复投递处理。持续超过能力的需求仍会积压。
- CQRS 分开写模型及读模型以优化不同用途，增加模型及同步工作，新鲜度取决于实际机制。它可以共享数据库，也可以省略事件溯源。保证细节见[一致性](./consistency.md)。
- 发布订阅为每个逻辑订阅提供独立投递路径。一个订阅内的竞争消费者可以分摊该订阅的工作。扇出增加投递及恢复工作。订阅持久化、重放及顺序取决于消息契约。
- BFF 为客户端定制聚合及交互，可以减少客户端往返、分开客户端专属策略，同时增加依赖并可能在多端重复逻辑。共享业务权威留在适当的负责人处。
- 管道通过显式中间结果连接阶段，阶段契约稳定时有利于独立处理及替换。受限阶段决定可持续吞吐。缓冲、序列化、部分输出及重启语义增加成本。阶段失败需要按已提交工作恢复。
- 插件结构把变化的扩展放在稳定内核契约后，支持真实扩展需要，同时增加契约演进、加载、生命周期及故障控制责任。进程内插件共享进程资源及故障后果，除非运行时提供更强隔离。

选择能以可承担协调成本解释关键情景的组合。内部模块化可以减少未来抽离范围。实际隔离要求可以直接决定所需运行边界。

## 表达软件视图

C4 的上下文层表示软件系统及外部参与者，container 表示应用或数据存储，component 表示 container 内的责任，code 表示实现细节。C4 container 是逻辑应用或数据存储抽象，可以有多个部署实例，也可以与其他应用共享运行时。[C4 container 定义](https://c4model.com/abstractions/container)将该抽象及部署分别说明。

部署视图表示实例、主机、区域、网络路径及故障域。时序表示调用、等待、未知结果及恢复。状态视图表示业务推进及权威。各图中的责任名称保持一致。

构造情景：订单模块及计费模块部署在一个应用内，一个数据库事务协调本地不变量。独立扩容的报表投影消费已提交变化。这结合了模块化单体及异步读处理。投影的独立性保留事务应用的权威。保证声明需要说明实际同步及新鲜度。

组织及决定权见[系统边界](../core/boundaries.md)。状态见[数据权威](./data.md)。具体传递方式见[消息](./selection/messaging.md)。
