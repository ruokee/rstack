# 系统架构

解释相互作用的部分怎样达成系统目的。系统可以包含软件、人员、流程、设施及外部组织。根据运行后果及需要保留的义务选择结构。

## 明确判断

确定系统对象、提供的结果、服务的人、外部环境及观察尺度。区分当前事实、期望结果、硬约束、偏好及假设。产品行为及优先级来自当前任务的权威材料。

沿一条重要场景追踪参与者、决定、状态变化、资源、交接及外部效果。既有系统使用实际记录、实现及运行证据。新系统从预期结果推导责任。围绕能够改变决定的部分继续调查。

事实来源随对象选择：

- 软件：相关代码、配置、数据契约、部署及运行记录。
- 服务：受理、接收、排队、完成、返工及投诉。
- 组织：决定权、实际协作、等待及责任转移。
- 设施：物理容量、运行条件、依赖、维护及失效。

文档承诺、实现行为及运行观察存在差异时分别说明，指出受影响的判断及解决关键差异所需的证据。历史意图依据当时记录。

## 解释机制

明确谁负责决定、权威信息、资源、接收及完成。定义关键交接的义务，包括部分完成、状态可见性及恢复责任。

推演会改变选择的运行情景，包括正常工作、相关负载变化、失效、恢复及过渡。把系统结果追溯到责任、协作或共享资源。说明什么机制建立了承诺的保证，以及保证止于哪里。

重要假设紧邻依赖它的判断，注明范围及失效后果。可用材料中的事实直接核对。估算给出输入、单位、时间窗口、边界及公式。构造示例明确标注。影响决定的产品能力按相关版本或日期核对一手资料。

存在实质取舍时比较候选，包含可行的现状方案。使用相同情景比较结果、采用及运行成本、风险和变化代价。给出推荐，说明接受的代价。尚未解决的目标冲突由用户决定。

## 交付判断

- 分析：说明现状结构、重要运行路径及有依据的约束。未知原因保留为待调查问题。
- 设计：给出推荐结构、关键责任、交接契约、运行后果及取舍。
- 评估：报告具体违反的约定、成立前提、后果、最强相关反证及修复方向。合理方案允许零问题结果。
- 选型：解释各可行候选怎样满足目标，说明采用及运行义务、退出条件。
- 演进：说明受影响边界、过渡责任、切换条件及恢复或退役安排。

沿用当前任务的格式及记录位置。视图及细节以支撑当前决定为准。可靠的现状说明可以完成分析请求。实施及交付遵循当前任务的范围和权限。

## 相邻职责

判断对象决定范围。同一进程内的冲突写入口可以需要架构判断。跨仓库的代码接口调整可以仍属于代码设计。

需要深入时，使用 `code-design` 处理类型、接口及内部依赖，`code-quality` 处理具体代码及质量设置，`ddd` 处理领域含义及限界上下文，`diagnose` 追查实际原因，`prototype` 为关键争议提供实验，`thinking-method` 提供通用推理方法。这些是可选参考，按宿主支持的方式取用。本包提供完成其架构判断所需的本地知识。当前工作流程负责协作、核验及交付。
