# 架构决定

按必须交付的结果及负责人能接受的代价选择结构。功能含义会塑造权威及失败处理，也决定可见功能。质量属性说明系统在给定条件下需要怎样运行。

## 明确可观察目标

把可靠、快、易维护等说法转成情景。说明条件、参与者或事件、受影响部分、预期响应，以及区分可接受结果的度量。数值依据当前目标。

构造情景：维修受理后发现缺件，工单继续对负责人可见，客户在约定响应窗口内收到更新承诺。软件中的对应情景可以要求调用方重启后仍能查到已完成退款。两者都需要机制及可观察结果。

区分硬约束、优化目标及偏好。法定义务、既有接口及预算上限可能排除候选。缩短等待或降低运行成本可以用于排序。目标冲突交给有权决定的人确认。

## 比较可行选择

现有安排能满足目标时将其纳入。比较会改变责任、资源使用、协作或生命周期成本的候选。局部问题已有确定机制时可以直接给出。

对相关候选采用相同的正常、负载、失效、恢复及过渡情景。将承诺收益追溯到机制。计入学习、采用、集成、人员、日常运行、故障处置、迁移及退出成本，记录实际由谁承担。

自建外购比较内部能力及时间、供应商契约、容量、依赖、生命周期及替换路径。差异化价值可以支持保留控制权，同时需要人员及资源。采购可以缩短采用时间，也增加合同及退出义务。

成本估算包含负载、单位、周期、固定及可变费用、不确定性。组件数量、团队规模或通用流量门槛是调查线索。当前要求及机制决定结论。

## 记录选择

沿用项目现有格式及位置。保留背景、选择、实质候选、理由、接受的后果及重审条件。说明被放弃的方案在什么条件下可能有用。

有意识的权宜需要具体后续成本及触发条件，例如人工核对工作量超过现有人员时间后替换该步骤。模糊的“技术债”标签给接手者留下的行动依据很少。需求、成本、依赖、生命周期或运行测量改变决定前提时重审。

## 核对保证

每项关键承诺都要说明什么机制阻止违反。责任可以通过具名角色及确认接受的交接建立。数据库约束可以保护唯一性。恢复流程依赖有效记录、资源及合格执行者。

已确认且可机械观察的约束，可以在有用时转成检查，并说明负载及范围。依赖检查通过建立被检查的依赖规则，性能证据需要给定负载及环境。开放判断采用对应证据，避免规定任意精确输出。

按实际契约及最强反证评估方案。报告缺陷前给出具体违反情景。机制满足已确认条件时保留零问题结果。新实验及实施遵循当前任务的范围和权限。
