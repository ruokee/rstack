# 系统演进

改变系统时交代必须保留的结果及义务。新目标、实际瓶颈、供应商退出、支持终止或成本变化，都可以触发结构重审。

## 定义替换对象

明确变化原因、保留结果、受影响参与者、可替换能力及已有义务。通过实际记录及契约核对旧安排隐含承担的工作。替代方案需要接住这些工作，或由有权负责人明确改变义务。

在完整切换及临时共存间选择。消费者能同步变更、在途工作可处理、停顿可接受时，完整切换可能更简单。共存可以减小每次变化，同时增加双系统运行、同步及协调。成本依据实际连续性及兼容需要判断。

## 安排过渡阶段

每阶段说明谁接收新工作、保管权威事实或物资、分配资源、确认完成及处理异常。定义在途工作怎样完成，以及下一参与者怎样接受责任。

构造服务情景：新维修商从指定日期接收预约。旧维修商按清单完成已受理工作，清单注明工单及持有备件。客户联系责任继续明确。转移工单需要接受记录、当前承诺及备件保管确认。只把两家维修商列在名单中会留下这些责任。

关键阶段说明进入条件、预期变化、完成证据及恢复条件。演练或有限上线用于解决真实不确定性，需要程度依据变化风险及已有证据。

## 保留恢复路径

恢复从实际当前状态出发。回到旧安排，需要它拥有当前事实、所需资源、有效契约及重新接管权。新方独自接受的新工作可能让直接返回留下缺口。按需要定义反向转移、核对或新方继续完成。

识别不可逆效果，例如已消耗物资、已完成付款或已给客户的承诺。这些需要业务有效的补偿或恢复安排。路由开关保留了已经发生的效果。

## 结束旧责任

剩余消费者及义务已经交代、保管权已转移、必要记录仍可取得后，退役旧能力。按实际环境结束过时排程、访问、供应承诺及运行工作。保留解释决定及恢复历史事实所需的记录。

记录改变了什么、新分配怎样满足目标、接受的运行成本及重审条件。兼容、并发回填、影子执行及权威切换的软件机制见[软件迁移](../software/migration.md)。
