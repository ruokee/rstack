# 系统分析

理解当前系统，直到足以回答本次问题。从目的和一件实际工作开始，调查决定结果的责任及协作。

## 追踪实际工作

选择有代表性的实例，确认起点、预期完成、参与者、决定、信息、资源及外部效果。包括等待及部分完成。服务体系沿受理记录追到接收及完成。设施体系沿运行需求追到设备及支持它的基础设施。软件沿入口追踪状态变化及依赖。

比较约定路径及实际记录。组织图说明正式责任，交接回执说明谁实际接收，代码建立实现路径，运行记录说明在观察条件下发生了哪些路径。注明观察窗口及案例选择，便于读者判断覆盖范围。

调查会影响所需结果的差异。构造情景：流程手册把缺件跟进交给受理岗位，维修日志显示技术人员反复联系供应商。现状说明保留正式分配及实际工作。差异指向责任含糊及维修能力占用，历史原因需要另有证据。

## 定位权威

对关键事实或决定，确认谁能创建、改变、确认及纠正。核对实际写入或批准路径。区分信息副本及其权威，区分协调工作及承担完成责任。

共享表、循环依赖或团队频繁联系都是调查信号。判断问题前先建立相关契约及实际后果。多个写入者在各自范围或协调规则明确时可以合理存在。

软件调查读取相关入口、依赖方向、状态存储、结构、配置、定时工作及部署。追踪解决当前问题需要的部分。AI 服务在影响运行时还要包括模型及上下文版本、工具执行、使用费用及持久化进度。

## 解释实际限制

将约束关联到路径、资源或义务。队列可能来自能力不足、输入缺失、批量规则或决定权阻塞。汇总数量会留下这些原因。寻找有区分力的观察，例如可开工与阻塞工作、处理与等待时间、不同负载的资源使用。

容量估算给出负载、单位、边界及时间窗口。假想负载变化注明前提。采用实际目标或会改变决定的情景，避免套用统一规模倍数。存量及流量判断见[系统动态](./dynamics.md)。

## 交付现状说明

说明系统目的及边界、关键责任、代表性运行路径、相关依赖、有依据的限制，以及影响问题的未知事实。视图用于澄清这些关系。

分别表达当前行为、推导后果及评价。解释结构的历史理由需要历史记录支持。分析可以在形成可靠说明及聚焦的待解问题后结束。根因调查及重新设计按本次范围继续。
