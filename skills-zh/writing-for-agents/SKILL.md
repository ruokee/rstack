本文适用于 Agent 阅读的各种内容，包括 Skill、`AGENTS.md`、Prompt、Tool/MCP 描述、subagent 指令，以及通过引用加载的文档。它们的封装形式不同，写作方法相同。目标是让 Agent 每次遵循相同的过程，从而使行为可预测。每次输出可以不同。

编写 Skill 时，读取 [Skill 机制](./SKILL-MECHANICS.md)，了解 frontmatter、description 触发条件、调用方式及路由 Skill。

## 上下文指针

上下文指针是 Agent 当前上下文中的一条引用，它指向上下文之外的材料，并说明何时读取。Skill 的 description，以及 `AGENTS.md` 中指向另一份文档的一行说明，都属于上下文指针。Agent 何时读取目标、能否稳定触发，取决于指针的措辞。如果必读材料被放在含糊的指针之后，就会造成执行差异。先明确指针的触发条件。只有这样仍然无效时，才把材料移入正文。

Skill 的 `description` 是最主要的 Trigger。按[触发描述](./SKILL-MECHANICS.md#触发描述)编写加载条件。

指针承担两项职责：说明材料是什么，列出应当触发读取的不同情况。每种情况都是文档处理的一条分支，不同执行过程可能进入不同分支。常驻指针中的每个词都会在每轮对话中占用上下文，因此要比正文更精简：

- 把引导词放在前面，让它在需要触发的位置发挥作用。
- 每条分支只写一个触发条件。同一条件的多个近义表达合并为一个，保留真正不同的分支。
- 删除正文已经说明的身份信息。

## 两类负担

每增加一份文档或一条指针，都会带来两类负担之一：

- 上下文负担。常驻内容占用 Agent 的上下文，例如 `AGENTS.md` 中的一行要求、Skill 的 description。无论是否触发，这些内容都会在每轮对话中消耗 token 和注意力。
- 认知负担。人需要记住有哪些文档，以及何时使用。人承担索引的职责。这是保留人的自主选择所需的成本，应当用在需要人判断的地方，其余地方则可以减少。

通过指针按需加载的材料，只需让指针本身常驻上下文。完全依赖人来记住的材料，其负担全部落在人身上。

## 信息层级

文档由两类内容组成：步骤描述按顺序执行的动作，参考材料提供按需查阅的定义、规则和事实。它们可以自由组合。操作流程可以全是步骤，审查规则或本 Skill 可以全是参考材料，也可以两者混合。关键在于按 Agent 需要信息的紧迫程度安排层级：

1. 文内步骤位于最直接的一层，说明做什么以及执行顺序。
2. 文内参考材料供执行时查阅。同一组规则可以平铺在同一层，例如一份审查清单中的各条规则。这种结构本身是合理的。
3. 外部参考材料放在独立文件中，通过上下文指针按需加载。文件可以与正文同目录，也可以放在其他位置供多份文档引用。

下放得太少，主文档会臃肿。下放得太多，Agent 需要的材料又会被藏起来。层级设计要处理这两种风险。

渐进式披露是把材料沿层级下放，移出主文件并放到指针之后，使顶层内容清楚易读。它的重点是保护信息层级。token 优化并非首要目标。判断是否应当下放，最直接的方法是看执行分支：所有分支都需要的内容放在正文，只有部分分支需要的内容按条件加载。对于包含步骤的文档，堆积参考材料会掩盖步骤，使 Agent 能否注意到步骤变得不稳定。这会影响执行行为。

同位组织处理同一文件内部的布局。信息层级决定材料放在哪一层，同位组织决定哪些内容放在一起。同一概念的定义、规则和注意事项应当放在同一标题下，让读者一次取得所需信息。按概念分组的文档更符合 Agent 的阅读方式。分散是把同一概念的不同部分拆到多处；重复则是把同一含义写在多处。

文档蔓延是另一种失败：每一行都有效且独特，全文仍然太长。内容过多会分散注意力，每增加一行也会增加保持相关性的维护成本。处理方法仍然是安排层级，将参考材料按需披露，并按分支或执行顺序拆分，使每条路径只携带自己需要的内容。

## 完成标准

每个步骤都应当有完成标准，让 Agent 判断何时结束。完成标准有两个关键属性：

- 清晰度。Agent 能否区分完成和未完成？含糊的边界，例如“已经理解”，容易导致提前结束。Agent 会把注意力转向完成这件事本身。眼前可见的后续步骤会吸引它继续向前，而清晰的完成标准能约束这种倾向。先把当前步骤的边界写清楚，这是成本最低的处理方法。只有边界确实难以明确，而且已经观察到抢跑时，才通过拆分流程隐藏后续步骤。隐藏必须跨越真实的上下文边界，例如交接或子 Agent 委派。内联调用会保留后续步骤的可见性。
- 要求强度。“逐一核对所有修改过的模型”比“生成变更清单”要求更深入的工作。要求强度会影响 Agent 实际投入的调查，这种作用来自措辞，也适用于参考材料。“每条规则都应用到”对规则清单的约束，类似“每个步骤都完成”对执行流程的约束，因此纯参考文档也可以要求完整覆盖。

有力的完成标准同时具备可检查性和完整性。

## 拆分时机

把一份文档拆成两份，会增加上下文负担或认知负担。拆分应当带来相应收益：

- 按执行顺序拆分。当后续步骤容易使 Agent 草率结束当前步骤时，将它们分开。暂时隐藏后续步骤，可以让 Agent 更充分地完成当前工作。反过来，合并流程会让后续步骤提前可见，增加提前结束的风险。
- 按调用方式拆分。这是 Skill 特有的情况，见 [Skill 机制](./SKILL-MECHANICS.md)。

## 引导词

引导词是模型在预训练中已经熟悉的简短概念，例如 lesson、fog of war、tracer bullets。Agent 可以用这些概念来组织执行方式。重复使用同一个词，而非反复写整句说明，可以逐渐形成分布在文档各处的定义，并利用模型已有的知识，以较少文字约束一类行为。自造词需要清楚定义，并额外支付解释成本。优先使用模型已经熟悉的概念。

引导词在两个位置发挥作用。在正文中，它帮助 Agent 反复采用同一种行为，也能在平铺的参考规则中指向一类关注点。在指针中，它帮助触发加载。当提示、文档和代码使用相同的词时，Agent 更容易把它们关联起来，并在需要时读取材料。

寻找适合用引导词改写的地方。例如，同一组三项要求重复出现，或者一条指针用整句表达一个概念，都可能压缩成一个词：

- “fast, deterministic, low-overhead”可以用 tight 概括，例如 a tight loop。
- “a loop you believe in”可以用 red 表达，把模糊的判断改为可观察的二元状态，即反馈循环是否因该缺陷而变红。

这样既减少文字，也给 Agent 更明确的行为线索。检查文档中哪些重复表达可以由已有概念替代。

否定式表达容易适得其反。禁止某种行为会先把这个行为带入上下文，并增强它的可见性。“不要想大象”会让大象成为注意力中心，较弱的否定修饰可能被忽略。优先直接描述目标行为，例如“注释写成一行”。只有难以用正向要求表达的硬性边界，才值得写成禁令。即使如此，也应当同时说明应当采取的行为。

## 修剪

- 每个含义只保留一个权威来源，使行为变化只需修改一处。重复表达同一含义会增加维护成本和上下文占用，也会让它显得比实际更重要。引导词则有意重复同一个词，以连接不同位置的定义。
- 环境也是权威来源，包括 `package.json` 中的脚本、配置文件、目录结构和 `--help` 输出。文档重复这些内容，相当于建立一份缓存。只有查找成本较高时，这份缓存才值得常驻。记录从环境中看不出来的约定、选择理由和隐含问题。通过一个文件或一条命令就能查到的事实，留在环境中维护。
- 逐行检查相关性。某一行是否仍然服务于文档的目标？纯背景介绍、本应按条件加载的分支，以及随行为变化而过时的内容，都可能失去相关性。较短的文档更容易维护。持续检查新增和保留内容，避免失效信息逐渐堆积。
- 逐句寻找无效指令，即模型默认就会遵守、因而无法改变行为的要求。判断标准是相对于模型默认行为是否有变化。争议应当通过实际运行文档解决。当一句话无法产生效果时，删除整句。引导词也需要同样检查：如果模型本来就会比较细致，“be thorough”可能无效，可以改用更有约束力的词，例如 relentless，而不必更换整套方法。
