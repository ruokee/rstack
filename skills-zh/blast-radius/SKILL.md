# 影响范围

从软件改动出发，沿真实依赖追踪消费者、持久数据及可观察行为。识别决定结论的前提，取得相称证据，明确剩余检查。简单调查可以在几段正文中完成以下步骤。

工具、角色、权限及交付规则沿用当前任务。修复、提交、发布及协作遵循该任务的范围。

## 1. 确定改动

读取请求、相关契约及改动。说明比较基线、候选标识及状态、目标行为，以及需要保持的行为。涵盖新增、修改、删除的接口、数据、配置及副作用。纯重构按行为保持契约评价。有意行为变化按已确认的新需求评价。

可以从 diff、提交范围、局部代码或具体方案开始。只有方案时，按拟议行为描述条件性影响及后续验收检查。已有实现时，追踪当前代码及实际运行条件。将拟议行为同运行观察分开表达。

从现有上下文取得具体对象。缺失信息会改变影响判断时再询问。按具体疑点读取相关历史，例如兼容承诺或特殊分支的适用原因。

能说明什么在什么条件下发生变化，并定位相应实现或方案后，进入下一步。

## 2. 追踪传播

从变化的操作或表示开始，追踪输入来源、直接使用者及下游消费者。每条关系说明传到下一处的值、状态、事件、约定或资源影响。按改动选择相关路径：

- 调用及发现。追踪间接调用、注册表、插件、反射、字符串名称、导入及生成的绑定。结合有效配置核对真实注册及查找规则。
- 数据表示。追踪 JSON 字段、数据库列、消息、文件格式、命令行输出及跨语言读取。检查生产者实际输出、各转换处保留的内容及消费者读取的表示。
- 历史状态。追踪持久化记录、旧消息、缓存及恢复过程怎样进入改动后的代码。检查已有数据怎样到达新读者。
- 运行顺序。追踪初始化、异步回调、微任务、取消、清理、提交及外部效果。确定真实顺序和资源持有者。驱逐条目可能排队执行清理，随后释放订阅。
- 有效配置。从声明到运行行为追踪默认值、环境差异、功能开关、构建产物及启用入口。禁用路径按实际激活条件评价。
- 外部依赖。检查锁定或实际安装的版本、本地补丁、包装层及实际调用的实现。依据这条有效路径确定行为。
- 部署关系。按项目确认的部署契约检查并存版本、读者、写者、离线客户端及在途消息。独立发布的消费者需要相应证据。数据改动分别检查旧数据进入新读者、新数据进入旧读者，以及回退后的可读性。已确认的停机切换会改变哪些组合实际可达。

持续追踪到可观察结果、真实消费者，或有证据说明变化已被隔离的边界。包装层保留公开输入、输出、错误及副作用时，可以结束传播。入口守卫排除触发条件，或消费者确实忽略所变字段，也可以作为停止依据。说明机制及适用条件。

搜索为空时，记录目录、名称及搜索方式覆盖的范围。动态发现、仓库外消费者及历史数据分别调查。对范围外的重要消费者，指出缺少的材料及其影响的兼容判断。取得其契约及行为之前，具体故障按条件表达。

重要影响均有可追溯路径，重要边界均有停止依据或具体证据缺口后，进入下一步。

## 3. 提炼关键前提

提取一旦不成立就会改变判断的事实。例如删除缓存是否触发回调，旧读者能否收到新写入的数据，包装层是否保留公开单位。

每个前提说明来源、适用条件、支撑的结论，以及能推翻它的观察。多个结论共享的前提集中检查。独立前提分别保留。缓存检查成功可以解决缓存前提。独立的存储格式前提需要对应证据。

区分已确认需求、观察事实、由实现推导的事实及调查者假设。检查最强的相关反证，例如真实入口守卫、包装层转换、版本差异或有效开关状态。需要深入判断正确性、变更安全或测试预期时，按需使用 `code-quality`。已观察到的故障需要调查原因时，按需使用 `diagnose`。本入口的方法可独立使用。

按后果、现实触发条件、暴露情况及恢复代价确定优先级。概率数字需要数据和明确统计口径。其余情况说明具体触发条件、适用群体及暴露情况。

重要结论均有依据，待查前提具体到可以确认或推翻后，进入下一步。

## 4. 获取证据

先提出能改变判断的问题及预期观察，再选择检查。按问题选择证据：

- 读取完整的相关源码、契约及控制流，确定静态关系、转换责任及路径可达性。
- 运行时依赖语义采用调用有效路径上真实实现的局部检查。保留候选、输入、相关环境及版本、实际结果和证据位置。
- 组件协作、配置或生命周期决定结果时，执行覆盖该关系的集成或应用操作。
- 视觉影响通过实际界面观察。状态及数据影响通过相关状态、返回值、持久结果或外部效果观察。
- 复用已有检查前，比较其候选、条件、输入、路径、断言及观察同当前问题的对应关系。成功结果按实际覆盖范围解释。生产者内部对象的断言覆盖该对象。传输字段发生变化时，需要经过序列化及消费者读取的证据。

预期结果来自需求、协议、业务规则或独立推导。选择能够区分正确行为及所查错误的检查。已有失败用例、前后对照或有针对性的反例可以提供这种区分。永久测试的新增沿用项目规则及当前请求。

执行遵循当前角色及权限。独立调查中，完成已授权且能改变判断的具体检查。嵌入既有验证流程时，将问题、输入、独立预期、实际路径及已有证据交给取证角色，复用其适用结果。

检查受阻时，记录实际原因，继续可完成的调查。入口启动失败属于该次检查的执行结果。原定行为检查标为待执行，并说明恢复条件。受影响结论保留缺失证据对应的条件。

可回答的问题已有相称证据，其余关键问题已有具体取证方式及前置条件后，进入下一步。

## 5. 形成结论

分别表达观察、推导及建议。引用能够定位当前候选中的代码、数据、配置、版本或运行结果。围绕当前问题组织答复，保留有用类别，空类别可以省略：

- 变更及范围。说明基线、行为差异及调查边界。
- 已确认影响。说明受影响的消费者或数据、传播机制、条件及可观察变化。有意变化保留其需求依据。
- 成立的风险。给出有依据条件下的失败路径、违反的契约、后果及证据。静态推导和实际故障分别标明。
- 已排除路径。保留检查过的疑点、排除依据及适用范围。
- 待确认前提。说明条件性影响、当前缺口，以及哪种证据会改变判断。
- 验证建议。说明行为、输入或操作、独立预期、对应路径及执行状态。

影响范围由消费者、数据及运行条件表达。文件数、改动行数及直接调用方数量用作定位线索。本次调查范围内零项成立风险是有效结果。

回退分别检查代码版本、数据、外部效果及部署关系。撤销提交可以恢复对应代码。已写入的数据及已完成的外部效果需要各自的恢复条件。例如，将写入对象的格式改动回退为只接受整数的读者，存储中的已写对象仍会保留。依据真实读写者、数据及部署契约判断恢复条件。

当前问题已有证据支持的结论，或者剩余关键缺口已明确到受影响判断及取证条件时，完成调查。继续调查的依据是一个尚可解决且会改变决定的问题。

## 示例

以下为构造情景。某导出接口将 JSON 字段 `retryAfterMs` 改为 `retry_after_ms`。已确认需求要求已有自动化客户端继续按相同字段读取。服务端所有类型引用均已更新。`tools/poller.py` 通过字典索引读取旧字段。

从服务端序列化的 JSON 追踪到 Python 读者。若响应缺少 `retryAfterMs`，读者会抛出 `KeyError`。这条路径违反兼容需求。定位真实编码器及消费者索引位置，检查序列化响应以核验关键前提。

有区分力的检查将真实导出响应传入消费者读取路径。独立预期为契约要求的原字段及其值。记录候选、输入、实际响应及消费者结果，或将这些信息交给指定的取证角色。

若包装层仍输出原字段，值及公开行为保持相同，则依据该转换收窄影响。内部改名可以在这个边界结束传播。
