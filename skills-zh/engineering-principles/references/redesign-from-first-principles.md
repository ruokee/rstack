# 从第一性原理重新设计

新增需求可能暴露原结构中的假设。用包含新增部分的完整需求评估受影响设计，像第一次为它选择结构一样作出判断。

例如，文档发布器增加定时发布。接收内容后立即返回公开 URL 的函数，可能隐含了立即发布的假设。考虑等待发布时调用方需要什么结果、谁负责调度，以及例子怎样说明该结果。单独增加计时器会留下这些问题。

从必需行为和约束出发，推导合适的职责及表示，再与现有设计比较。保留已经适用的结构。重新设计限于受影响且获准的范围。

将选定契约落实到类型、使用方、文档、例子及理由中。完整结果可能需要修改最初接到需求的函数之外的位置。采用新契约时，参见[先迁移再清理](./migrate-then-clean-up.md)。

这项判断以已确立的需求为起点。故障背后的事实假设仍有疑问时，使用[质疑前提](./attack-the-premise.md)。
