# 绘制项目功能地图

交付一份可导航的索引。每条记录对应一项用户操作和一个阅读起点。开发者扫一眼功能名称，就能选中一项并直接去读代码。一次性定位找到答案即可；规划请求可以直接使用项目已有的索引。

## 确定范围

确认版本、请求范围、文档语言要求和读者日常打开的索引。已有索引能容纳缺少的指引时，直接补入。全项目建图从实际注册位置和用户指南列出公开入口。局部建图写明所含范围及影响使用的缺口。

## 追踪用户操作

按用户想得到的结果归组。把两个公开入口列为同一操作的选项前，比较各自需要的输入、影响的对象和操作后的状态。只有任取其一都能达成标题所说的结果，才列在同一项。即使共用实现，不同操作也分别列项。相关条目可以放在同一个功能区小标题下，各条目保留自己的入口。

采用真实需求、命令、路由、菜单或公开 API 中的用语。从每个入口沿分发路径找到决定行为的符号。多个入口共用处理函数时，核对各调用方实际传入的参数。共享规则按需链接一次。指南与实际分支有出入时，指出具体差异并链接决定行为的源码。

## 编写索引

先写出覆盖范围内最短的完整索引。每条用一个短列表项写清：**用户操作**、公开入口、符号链接，以及到那里看什么。第二个位置会改变读者选择时才加上。用功能区作小标题，较大的功能区可以把条目拆到链接页。文件链接相对于当前文档。

实际项目的地图条目可以这样写：

- **理解搜索 Trace 无结果的提示。** `langwatch trace search` 看 [CLI 的 `emptySearchHint`](https://github.com/langwatch/langwatch/blob/ea636c6f90a5934a6913d61d6408c092ac9359bd/sdks/typescript/src/cli/commands/traces/search.ts)；`search_traces` 看 [MCP 工具的 `buildEmptyResult`](https://github.com/langwatch/langwatch/blob/ea636c6f90a5934a6913d61d6408c092ac9359bd/mcp/typescript/src/tools/search-traces.ts)。

每条到这里即可。不同模式或阶段产生不同效果时，分别指向决定效果的位置。错误码清单、参数语义、行为保证及操作顺序由权威参考持有，按需链接。访问条件改变可用入口时，依据实际分支写清适用范围。依赖运行状态的结论标明条件。

按项目要求的语言完成地图，每个语言版本在日常导航中添加一条简短的发现链接。先检查索引能否使用，只在实际查找受阻时扩写相应条目。

## 修订已有地图

先查清具体变化。在指定项目内，对照受影响的旧条目、当前公开接口及实现。已有版本差异或发布说明时使用它们。没有历史版本时，从当前命令或路由声明及其参考资料找出旧条目缺少或已经失效的具体能力，把它与同主题下沿用的规则分开。

对每项受影响的用户操作，找出原有阅读路径、当前可选的行为及决定它的符号。核对所有提供同一变化的入口。新旧选项存在优先关系时，一起核对。共用的说明只更新一处，各入口都要能找到它。名称变更、实现移动或入口下线，调整相应导航即可。拟议功能保留在计划中。

只改到读者能找到变化后的行为为止。相邻机制沿用已有参考。用旧条目对照修订结果：每条新增陈述都要解释这次变化，并符合决定结果的分支。顺带加上的说明直接移出条目，避免推广到其他输入形式。按项目要求同步各语言版本。最后从导航走查受影响的入口，核对保留的路径仍可使用。

## 检查阅读路径

将完成的索引与公开入口清单核对。从项目导航出发，用用户日常说法选一条代表性需求，打开所指的定义。它能决定所问行为，或让人直接找到决定行为的位置吗？最容易混淆的另一种情况是否走其他路径？修正会把人带错的指引。与定位无关的行为描述改为链接到决定行为的源码。范围内每组都有可用阅读路径后，交付地图、覆盖范围和剩余缺口。
