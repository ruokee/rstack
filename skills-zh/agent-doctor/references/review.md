# 复核诊断

先读原请求和原答，找出真正会改变维护决定的原句。逐项给出“原答说什么、现有材料能确认什么、该怎样改写”。正确的决定也可能用了错误的理由。尤其注意“删掉就会……”：有可比的行为证据时，按受测范围判断；只有文件或单组记录时，即使建议暂留，也要把删后行为改为未知，交付检验该预测的具体办法。

复核原答提出的每条补查，尤其是“查 X，**或者**看 Y”这类替代方案。逐个点名它引用的样本：它属于哪组？哪条记录证明这个条件？看到结果后，还有什么解释也说得通？把不适用的样本和原因写进复核结论。

## 分开不同的问题

对原答提出的每项检查，补完“这项结果足以判断……”这句话，只写这项结果确实能区分的事实。下面两个问题所需的证据不同：

- **谁做了这次改动？** 给出三项能对在一起的证据：同一个事件、可识别的写入者、它实际写入的具体内容。用成品核实该变更。检验原答列出的每种备选记录是否三项齐全。前后稿加退出码只说明期间有变化、程序也运行过；普通输出只有记下实际写入才算写入证据。换一场重新采集只能解释新事件。旧事件找不到关联记录，就明确交付“这次写入者未知”。
- **停用这一步会怎样？** 从同一代表性输入的一组已确认启用和停用的对照开始。历史写入者可以继续记为未知。即使查明了一次写入者，也没有因此得到停用组的结果。用[使用证据](./usage.md)核对原答的样本及判定规则能否说明交付是否合格、是否增加人工返工。

每项未决问题只交付一个能回答它的下一步。用“**为决定是否停用：**……”写配对检查和结果判据；另有来源争议时，用“**为查明当次写入者：**……”写所缺的可归属记录。两项可以独立进行。以这些检查收尾，避免后面的行动顺序与已经给出的证据判断冲突。

## 交付修正判断

给出可以直接替换原句的判断，保留有据发现。若原答对行为作了预测，即使当前建议是暂留，也要用本案的任务、参与者和产物写出对照。提出方案与实际运行分开：

1. **固定要求，只改手段。** 两组遵守同一业务要求，由同一执行者处理同一份确实需要该行为的输入。删提示的检查比较 A 实际收到一处完整提示与 B 实际收到零处提示，业务要求在两组始终有效。若连业务要求也要取消，由规则负责人另行决定。对可开关的步骤，则分别核对 A 确实执行、B 确实停用。点名不适合作对照的样本和原因。
2. **合格。** 从原要求分别取出“必须怎样做”和“必须交出什么”。对每一项过程要求，说出能看到动作实际发生的记录；对每一项产物要求，指出交付中要核对的内容。比如两个签名只能说明有两个签名，不能据此认定进行了两次独立审阅。若过程不可观察，保留未知，不能用产物数量替它打勾。
3. **比较两组实际完成的工作。** 每组先按同一标准判过程与产物，再计正常流程中人补做或改错的工作量；人工返工是结果，A、B 都应如实保留。只有输入、启停或其他既定条件未落实时，才判该样本无法回答这个问题。A 合格而 B 退化，保留 A；两组都合格且 B 不增加返工，才考虑在受测任务和模型上采用 B；两边都失败就查共同原因。对照条件或结果有缺口就暂留。一次配对只支持本次比较。

例如，原答称删去舍入提示会改变发票金额。把同一份含小数明细的发票交给实际部署的模型：A 保留提示，B 只删去唯一一处舍入提示。先核对两份输入，再按发票规则核对每行的舍入操作、对应金额和总额。总额碰巧相同，仍可能有两行的错误互相抵消。
