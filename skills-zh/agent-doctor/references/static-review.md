# 静态审查

从目标读者实际拿到的入口开始。选一项这份资产声称支持的任务，一直走到交付物。遇到分支，看读者靠什么判断要不要进入。遇到动作，看所需输入和说明能否在动手前拿到。一句话允许两种实际做法时，指出两种做法会在哪一步产生不同结果。遇到引用，从分发包内引用文件所在的位置解析路径。断链导致读者走不下去时，引用链接原文并给出缺失路径。

## 审查重复规则

引出两处原文，核对各自的适用条件、执行者、动作和交付物。保留任一处独有的条件或要求。若两处规定同一动作，选定一处维护规则，让另一处指向它；分别从两个入口出发，检查读者能否在动手前找到规则。指出两份文字分开维护时哪项要求可能发生分歧。

若两条规则冲突，举出一个读者会采取不同动作的场景，核对哪条要求适用。需要维护者取舍时，先说清要决定什么，再建议归并文字。

每项重复发现以两个分别作答的结论收尾。即使对照尚待执行，也要用本次任务把对照说具体：

- **两处 → 一处：** 指出保留规则的位置、可达的入口和必须保留的完整要求。这回答能否归并；两版读者都看得到规则。
- **一处 → 零处：** 以归并后的版本为 A。B 只改一项：让读者收到的整套任务材料中该条提示为零处。检查是否还有同义指令，再把 B 当作无提示组。在答复中写出 A 有一处、B 有零处、两组共用的目标模型和代表性任务，以及两份交付都要核对的动作和产物。型号未知时，以实际部署的模型为准。只有文件时建议保留 A。已有行为对照时，用[使用证据](./usage.md)判断。

删去提示后，原要求仍然有效。取消要求本身由负责这项规则的人另行决定。
